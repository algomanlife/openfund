# Payment incident — 2026-11-18 real purchases (v0.7.0)

Status: **open**. Both cases still need operator reconciliation in
production. No balance was changed and no challenge was provisioned by this
investigation.

## Sources and limits

- **Public chain data** (read-only public RPC queries, 2026-11-18). The
  inbound USDC/USDT Transfer logs were scanned for the public EVM treasury
  `0x2BB7c512Bb3bADfCC543D5E5309d98872b10E6B9` <!-- gitleaks:allow: public treasury address -->
  ([owner setup](OWNER_SETUP.md)) over the preceding ~36–40 hours.
- **Not available to this investigation:** the production database
  (orders, coupon snapshots, `payment_attempts`, `depay_events`), the
  owner's transaction hashes and the screenshots. Order ids and coupon
  snapshots are therefore **not** correlated here.

## Test A — DePay (Arbitrum One)

On-chain facts for transaction
[`0x8806874dd0085f2d44e57336c379d24af6ddf545fafbac8cd72b770dcc4444fe`](https://arbiscan.io/tx/0x8806874dd0085f2d44e57336c379d24af6ddf545fafbac8cd72b770dcc4444fe):

| Item | Value |
|---|---|
| Block / time | 525328834 · 2026-11-18 13:04:06 UTC (14 minutes after v0.7.0 was published) |
| Status | success |
| Paying account | `0x13a184a16ebeae761160ebe1716e93ffc571f0ea` (smart-contract account; `tx.from` `0xb42f…ead6` is a relayer and `tx.to` `0xdb9b…7db3` is not the token or the router) |
| Payer token | 84.23 ARB, swapped to USDC through a Uniswap v3 pool by the DePay router `0x328f…9271` |
| Router received | **10.853829 USDC** |
| Treasury received | **10.638000 USDC** (one Transfer log, router → treasury) |
| Kept by the router | 0.215829 USDC (plus 0.000681 ARB swap remainder) |
| Other transfer | 0.2349 ARB from the payer account to `0xe347…1964` (probably the relayer gas payment; unverified) |

**Correlation.** The reported order total was 10.80 (screenshot), and
10.638 = 10.80 × 0.985 exactly. The order id is in the signed DePay delivery
stored in production (`depay_events.purchase_order_id`), which was not
available here. Confirm it with the Backstage lookup by transaction hash
before reconciling.

**Cause of the shortfall.**

- DePay's router delivered 1.5% less than the requested settlement amount
  and kept the difference.
- This is consistent with a percentage deducted from the receiver amount
  (a DePay fee), but DePay's fee documentation could not be read
  (client-side page), so the fee model is **not verified**.
- Token decimals are not the cause: native Arbitrum USDC has 6 decimals, and
  the verifier read and compared them.
- Correlation is not the cause either: there is a single settling log to the
  configured receiver.

**Why Openfund showed "Verification Pending" and activated nothing.**

1. The verifier (correctly) measured 10.638 < 10.80 and rejected the attempt
   as `insufficient_amount`, classified `underpayment` and queued for review.
   The contract-wallet route was accepted because DePay attested the
   payment.
2. The signed DePay hint had already moved the order to `payment_detected`.
   Nothing moved it back after the rejection.
3. `checkoutStatus.ts` checked `payment_detected` before the rejected attempt,
   so the page said "Verification Pending" while the error was
   `insufficient_amount`.
4. There was no partial-payment path. The customer could not pay the
   remaining 0.162, and an operator could only record a review note.

**Fixed by Openfund Pay (unreleased).**

- The same transaction now settles as *Partially Paid — Remaining 0.162
  USDC* (`openfund-pay.test.mjs` P03/P04 and P23 reproduce it).
- The status precedence is corrected.
- DePay is off for new payments.

**Reconciliation, after release and with owner authorization:**

1. Backstage → Payments → Transaction investigation → search by this hash.
   Confirm the order and its coupon snapshot.
2. Reverify the attempt. The engine records 10.638 as a partial payment.
3. Either the customer pays the remaining balance (Complete Remaining
   Payment), or the owner decides a documented exception. No force-confirm
   exists.

## Test B — manual transfer (~$10)

- **No matching inbound stablecoin transfer was found** to the EVM treasury
  in the scanned window on Arbitrum (USDC, USDT, USDC.e), Base (USDC),
  Optimism (USDC, USDT), Polygon (USDC, USDT) and BNB Chain (USDC, USDT).
  The only inbound transfer was Test A.
- The Solana treasury `9U7cmxeHzLYBRh5gWxgzsteP8hTfZSQMfoHKSN6SQSpM`
  <!-- gitleaks:allow: public treasury address --> has **no SPL token account**,
  so it received no SPL USDC.
- **Ethereum mainnet was not scanned** (the public endpoints refused).

Possible explanations, none confirmed:

- the transfer was on Ethereum mainnet;
- it went to a different address;
- it used a native coin or another token;
- it is older than the window;
- the owner is remembering Test A.

Under v0.7.0, even a correct manual transfer is invisible until its hash is
submitted: there was no discovery.

**Needed to close:** the transaction hash or the sending wallet and network.
With Openfund Pay deployed, the watcher records the transfer on its own (set
`watchFromBlock` to cover 2026-11-18). If the sender is the SIWE wallet of
exactly one open order, it is attributed automatically. Otherwise it appears
under Backstage → Deposits to review.
